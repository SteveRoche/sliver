# CLAUDE.md

## Project

A Typst-based Zettelkasten notetaking desktop app (Tauri 2 + SolidJS + TypeScript, Rust crates for Typst and the vault).

## Decisions

- **Native only:** Windows, macOS and Linux via Tauri. There is no browser build, so don't add browser fallbacks or conditions.
- **Vault layout:** notes are `<uuid>.typ` files in folders, which are plain directories at any depth under the vault root (`Inbox/`, `Projects/Sliver/`); filenames never come from titles, and links never contain paths, so moving a file breaks nothing. The scan skips anything starting with a dot; every other file that isn't a `<uuid>.typ` note is an **asset** (images, PDFs, data, other `.typ` files). Everything else lives under `.sliver/`: `pkg/<namespace>/<name>-<version>.tar.gz` (Typst packages exactly as downloaded), `tmp/` (atomic-write staging: temp file, `sync_all`, rename), `workspace.json` (open tabs, active tab, pane sizes), `settings.json`, `theme.typ` (light theme colours, regenerated on open), `preambles/` (`common.typ`, `kinds/<kind>.typ`), `templates/` (`default.typ`, `kinds/<kind>.typ`), `references.bib` (cited Zotero entries), `styles/` (custom CSL files), `sync/` (this device's sync state, never synced: `config.json` with the vault's sync id and paired devices, `base/<device>.json`, `texts/`, `local.json`).
- **Note files are the only source of truth; there is no database.** Each note starts with a plain-Typst header, `#metadata((title: "…", address: "1.1a", tags: ("…",), kind: "…")) <note>` (optionally `citation-style: "…"`, read only by the preview wrapper). It has no imports, compiles anywhere, and its known fields must be literals. On vault open every header is parsed with `typst-syntax` (no evaluation) into an in-memory index: about 23 µs per note, versus about 2.7 ms to compile one. Anything derived (tree, backlinks, search) is computed from the files, never stored. Renaming edits only the title literal (`set_title`). Titles are unique across the whole vault, so a title names exactly one note, compared as links match them: trimmed, case-insensitive, curly quotes as straight (`title_key`, `titleKey`). Creating and renaming refuse a clash (`require_title_free`; the prompts show `titleClash` as they type, naming the folder of the note that has it); moving never changes a title, so it never clashes. Untitled notes never clash, and clashes from edits outside the app (or in a note's header) are a sidebar warning.
- **The Zettelkasten** is one ordinary, renamable folder (`Zettelkasten/` in new vaults), identified by a `.zettelkasten` marker file inside it so a rename anywhere (even in Finder) keeps it. The marker also holds the sections (`sections.rs`: `#let sections = ("1": "Probability", "4-5": "Writing")`, read with `typst-syntax`; empty without sections). Exactly one per vault (extra markers get a warning; a vault without one offers "Use as Zettelkasten" on a folder); it can't be deleted from the app and holds no subfolders. Only notes in it have addresses; other folders are flat lists sorted by title. Mismatches (an address outside it, a folder inside it, a duplicate uuid) are warnings in the sidebar, never errors, since files can be edited outside the app.
- **Note identity:** every note has a permanent uuid and, in the Zettelkasten, a **Zettelkasten address**, a Folgezettel in Bob Doto's style.
  - **Sequences and sections:** the first number of an address is a **sequence** (`4` in `4.2a`), not a note: notes start one level below it (`4.1`, `4.2`). A sequence exists while it has notes; a new one takes the number after the last (`Placement::NewSequence`, `(last + 1).1`; "New sequence" in the address picker, and what a drop onto the Zettelkasten folder does). Only notes are linkable: `[[4]]` is never a link to anything, and a note whose header says `address: "4"` gets a warning ("a sequence, not a note") and sits unaddressed. A **section** is an optional named heading over one or more consecutive sequences (`4-5`), stored in the `.zettelkasten` marker (`sections.rs`). It's made by marking notes in the sidebar (see the sidebar below) and "Make sequences 4–5 a section…" from the context menu of a marked note (when every marked note is an addressed Zettelkasten note) or of any Zettelkasten note; it can't overlap another section and needs notes in its range. Its context menu renames it or removes the heading (notes untouched). A section is trimmed to the sequences in it that still have notes and is gone once none do (`write_sections` after deletes and moves); there's no creating an empty one. The app never renumbers sequences into a section (adding a sequence to an earlier section isn't supported yet). A sequence emptied of notes leaves its number unused: a gap the user accepted, the one exception to the no-gaps rule.
  - Below the sequence number, numbers and letters alternate: `1.1`, `1.1a`, `1.1a1`, `1.1a2`, `1.1b`, `1.2`, … Letters are bijective base 26 (`z` → `aa`). A sequence's first-level notes (`1.1`, `1.2`) have no parent note; they're asides of each other.
  - Two ways to add a note after an existing one (the user's terms; use them in UI and code): a **next note** goes one level deeper (`1.1a` → `1.1a1`, `Placement::Next`, `Address::first_child`); an **aside** takes the next sibling (`1.1a` → `1.1b`, `Placement::Aside`, `Address::next_sibling`). Never call them "continuation" or "branch". A taken address moves on to the next free sibling. The app never creates a gap (an orphan like `1.3a1` without `1.3a`, or a skipped sibling or number): an orphan blocks its missing parent forever, since an address with a note under it is never free. Gaps from edits outside the app are tolerated, not fixed.
  - Sorting by address gives the tree's order. Notes whose parent address is missing attach to their nearest existing ancestor; unaddressed notes come last. A free address is one that no note has and no note lies under (an orphan `3.2a1` blocks `3.2a`).
  - Notes move between places explicitly (`vault/moves.rs`): **filing** a folder note gives it an address and moves its file into the Zettelkasten; **re-addressing** moves a Zettelkasten note with its whole subtree, renumbered by prefix (`Address::rebase`); **unfiling** to a folder drops the address (the notes under it stay and reattach to the nearest ancestor). Every `[[old address]]` link in the vault is then rewritten (to the new address, or to the uuid when unfiling), after a confirmation that `plan_move` feeds. Not transactional across files: a failure partway leaves stale links (shown broken), never a half-written file.
  - The sidebar is one folder tree: folders indent (they are a hierarchy, and the whole folder row folds; folded folders persist in `workspace.json`), with an indent guide (a vertical line below the folder's icon, setting `indentGuides`) along an unfolded folder's rows, but inside the Zettelkasten the address tree shows trains of thought, not a hierarchy: no indentation and no fold icons. Sections are heading rows (range and name, bold) among the sequences in number order; clicking one folds it (not persisted), and its notes indent one level (a grouping, like a folder, so the sequences after it don't look like part of it). Notes without a valid address come last. Clicking a note's address folds or unfolds the notes under it; folded addresses are drawn brighter (`--folded`). The rest of the row opens the note in the focused pane's current tab (`expandOnClick={false}`); Cmd/Ctrl-click, middle-click and the context menu's "Open in new tab" open a new tab. Up and Down (and j and k with Vim on) move between the visible rows and open a note in place after a short pause (`OPEN_DELAY_MS`, so holding a key doesn't open every note on the way). Shift-click and Shift+Up/Down mark the run of visible notes, in any folder, from the last row clicked or moved to (`markRun`; a plain click, plain move or Escape clears the marks). A context menu opened on a marked note acts on all of them (`menuNotes`: move to folder, delete, make section), and one opened on an unmarked note clears the marks. The rows are a Solid store reconciled by row id (`folder:`, `section:`, `asset:` prefixes, note uuids), so a refreshed tree updates only the rows that changed instead of remounting them all. Notes and files can be dragged onto folders and note rows (pointer events, `treeDragging`): onto the Zettelkasten (or a section heading) a folder note starts a new sequence, onto a Zettelkasten note it becomes its next note or aside (asked), onto another folder (or a note in one) it moves there, with the usual confirmations. A marked note drags every marked note, and several notes only go into a folder other than the Zettelkasten. Folders drag into other folders (`move_folder`, which shares `relocate_folder` with renaming, so paths into it are rewritten after the same confirmation): never into the Zettelkasten or into themselves, and the Zettelkasten only to the vault root. A row where a drop would do nothing isn't highlighted (`dropTargetFor`).
- **Wikilinks:** `[[target]]` or `[[target|custom text]]`, where the target is an address or, for unaddressed notes, a uuid. Titles never go in links: they'd need rewriting on rename, can be ambiguous, and can contain markup characters (and `|`).
  - In the source it's plain Typst text. In the app each note compiles through a wrapper main (`preview_main`) that applies the `wikilinks` show rule from the generated `/.sliver/links.typ` (`link_library`, only the rule and the link-display setting) with the note's own link table `/.sliver/links/<id>.typ` (`link_table`: just the targets the note links to, resolved to id, title and address), so neither grows with the vault. It renders `sliver://<uuid>` links labelled with the target's current title (or address, per the `linkDisplay` setting "Wikilink text", which governs the editor too), and broken targets in red. A session resends its table when its text links to a different set of targets (found with the show rule's own regex, before the compile) and, when a save or a change on disk alters the tree (`refreshTree`), for the open notes whose targets now resolve differently (another note, title or address, or none; `linksChangedIn`), which also recompile and redraw their editor's links (`linksChanged`); the others are left alone. Calls to `refreshTree` while a fetch runs share one more fetch after it. The preview never rewrites note sources, so diagnostics keep their positions; the app rewrites other notes' links only on an explicit, confirmed move.
  - Broken links create notes: Mod-click on one (editor or preview, where the rule renders it as a red `sliver-new:<target>` link; a plain click does nothing), or Mod+Enter in the editor ("Follow link at cursor", `editor.followLink`, which follows working links too, in place; Mod+Shift+Enter in a new tab), runs `followBrokenLink`. A title that notes have (case-insensitive, curly and straight quotes alike (`plainQuotes`)) asks which one to link to, listed with their folders, or to create another (the new-linked-note dialog); a title no note has (an **uninitialized link**) creates the note in the folder chosen in settings (the vault's new-note folder (newNoteFolder)). An address creates the note there only when that leaves no gap (`place_for_address`: the next note of the nearest existing ancestor, else an aside to the last first-level note of its sequence, else a new sequence); otherwise it offers that address instead, or a note titled as the target. A uuid whose note is gone counts as the title it had, if known (`formerTitle`), else it does nothing. Then every link to the target in the linking note (only that note) is pointed at the new one, its address or uuid, keeping custom text (`retarget`, one undo step in the editor).
  - Deleting notes (a note, or a folder with its notes) rewrites links to them in every note to their titles (`orphaned_links` taken before the delete, then `unlink`; `title_target` collapses whitespace and, when the title wouldn't read back as a plain-text title target, keeps only letters, digits and plain punctuation, "Untitled" when nothing's left), so they become uninitialized links. `delete_note` and `delete_folder` (`FolderDeletion`) return the notes whose files changed. A uuid of a note deleted outside the app (or before the rewrite) still never shows: the frontend remembers every note's last title this session (`formerTitle`), link tables list such uuids with `id: none` and the former title (`link_table`'s `former`), and the preview draws them broken, as that title.
  - Backlinks come from a syntax-tree scan (`links_in`) that accepts only plain text (and `'`/`"`, which parse as smart quotes) between the brackets, which is also all the regex rule can match; raw text is excluded in both. Known limits: styled text inside `[[...]]` doesn't form a link, and `\[\[x\]\]` still renders as a link (use raw for literal brackets).
- **Assets** (`vault/files.rs`, `paths.rs`): files in the vault that aren't notes. The sidebar lists them under their folder after its notes; images (png, jpg, gif, svg, webp, bmp, avif) open in a tab of their own (`Tab.asset`, `AssetView`, at most one tab per image), anything else in the system's app (`open_asset`). The context menu opens, copies the path, renames, moves and deletes.
  - Notes refer to them by **vault-absolute path** (`#image("/Projects/Sliver/diagram.png")`): every note compiles as `/notes/<id>.typ`, so a relative path would resolve against `/notes/`, not the note's folder. The editor warns about relative paths in notes (`analyze`'s `relativePaths`, squiggles via `setLint`), as preambles already do. Assets keep their own names (no uuids).
  - Moving or renaming an asset, or renaming a folder, in the app rewrites the string literals naming it (or something under it) in notes, preambles and templates (`rewrite_paths`; any string literal in code, so `#let logo = "/a.png"` too, never markup or raw), after a confirmation fed by `plan_path_move` when there's anything to rewrite. Not covered: moves outside the app (the preview shows Typst's "file not found") and computed paths (`dir + "/x.png"`).
  - The compiler gets files on demand: a compile reports project files it read but lacks (`missing_files`), the compiler host reads them from the vault, adds them (`set_file`, or `set_source` for `.typ`) and compiles again within the same call (`Host::compile`); files the vault doesn't have are remembered as absent until they change. A changed asset is dropped from the engine (`forgetFile`) and the previews that read it recompile.
  - Adding: dropping files from Finder onto a sidebar folder (or a row in it) copies them there; pasting an image into a note, or dropping files onto its editor, saves them where `attachmentLocation` says (vault root, the note's folder, or `attachmentFolder`, `Attachments/` by default, created on first use) and inserts `#image("/path")` (images Typst reads, PDF included) or the path as a string (`#"/data.csv"`, to wrap in `csv(...)` and so on). Pasted images are named `Pasted image <YYYYMMDDHHmmss>.png`; a taken name gets a number (`logo 1.png`). Finder drops come through Tauri's native drag-drop event (`fileDrop.ts`), not HTML5 drops.
- **Changes outside the app** (`src-tauri/src/watch.rs`, `notify-debouncer-full`): the open vault is watched recursively (debounced 300 ms; hidden paths and `.sliver/` other than preambles are ignored). On events the backend rescans (`Vault::refresh`): it walks the tree, rereads only notes whose stamp (mtime, size) changed, and reports notes whose text hash changed, removed notes, changed assets, tree changes and preamble changes (`vault-changed`). The app's own writes record their stamp and hash, so they're never reported, and events whose paths the index already agrees with (`Vault::matches_disk`: a note or asset with its recorded stamp, a missing path the index has nothing at, a known folder) cause no rescan at all, so an autosave costs no walk. The debouncer runs without a file id cache (`NoCache`): the default one walks the whole vault when the watch starts, only to pair up renames. The frontend (`applyDiskChanges`) refreshes the tree and links, reloads open notes without unsaved edits (`loadFromDisk`, which doesn't save back), and shows a notice on ones with unsaved edits ("Keep mine" saves over the file, "Load from disk"; for a deleted file "Restore it" or "Close it"); autosave holds off while a conflict is open. Closing such a tab still saves the editor's text.
- **Sync** (feature `sync`, off by default; `crates/sliver-vault/src/vault/sync.rs` for the vault side, `src-tauri/src/sync/` for the networking over `iroh`): a vault syncs directly between the user's devices, with no server holding notes. iroh connections are QUIC, end-to-end encrypted, dialled by device id (n0's public relays and address lookup; they see only encrypted traffic).
  - **Model:** state based, like Unison, no op log. Each device keeps a **base** per paired device: every entry as both last agreed. An entry is `note:<uuid>` (content hash and folder, so a move isn't a delete plus an add), `file:<path>` (assets, `.zettelkasten` markers, `.sliver/` `preambles/`, `templates/`, `styles/`, `settings.json`, `references.bib`) or `dir:<path>`; hashes are blake3 (`DefaultHasher` isn't stable across builds), cached by stamp in `local.json`. Against the base: one side changed, it wins; deleted on one side and untouched on the other, the delete wins; deleted on one and changed on the other, the change wins; a note both changed is merged line-wise against the base text (`diffy`; base texts are kept in `texts/` and collected when no base needs them), else the local text stays and the remote one becomes a **conflict copy** (new uuid, title `… (conflict, <device>)`, no address); a plain asset both changed keeps a copy beside it (`a (conflict, <device>).png`), hidden files keep the local one. Both moved a note: the dialing side's folder wins.
  - **Rounds** (`protocol.rs`, ALPN `sliver/sync/1`, one stream): only the dialing side decides (`plan`, `sync_round`), so the two sides can't disagree; it pulls what it needs, applies its own ops, pushes the other side's, and both record the same new base, except keys whose op failed on either side. Every op carries the state its side had at the start of the round and is skipped if the entry changed since (an edit mid-round is never overwritten; the next round settles it), so a round dropped halfway is harmless. One round per device pair at a time; both dialling at once get `Busy` and retry after a random pause. Remote keys are checked against what syncs (no writing outside the vault or into the rest of `.sliver/`).
  - **Applying** goes through the outside-changes path: sync writes the files (`apply_sync`, atomic writes, deletes to the trash), rescans (`Vault::refresh`) and emits `vault-changed`, so `applyDiskChanges` reloads notes or shows its conflict notice; `sync-applied` covers what the index doesn't (settings, references, styles reload).
  - **When:** the service (endpoint and router, `service.rs`) runs while a vault with paired devices (or one being paired) is open. The watcher signals every relevant change, the app's own writes too (before the `matches_disk` filter), and a round runs with every device 2 s after changes settle and every minute; an unreachable device backs off up to 5 min.
  - **Pairing** (`pair.rs`, ALPN `sliver/pair/1`): Settings › Sync › "Pair a device…" shows a ticket (`sliver` + base32 of the endpoint address, the vault's sync id and a one-time token, valid 5 minutes while shown). "Join a vault from another device…" (welcome screen, palette) takes it and an empty folder, pairs, writes only `.sliver/sync/config.json` (`prepare_join`) and opens the folder; its first round as the dialing side lets the other side win wherever both have a file without a base (`joining`), so the starter files a vault gets on open don't replace the other device's. Only paired devices may connect, and only for their vault. Pairing is pairwise: devices paired with the same device sync through it.
  - **Device identity** is per machine, in the app config dir (`device.key`, the iroh secret key; `device.json`, the name shown to other devices and in conflict copies), never in a vault.
- **Crates:** `sliver-typst` is the compile/render service, native only, hosted by the backend (`src-tauri/src/compiler.rs`). `sliver-vault` (native) owns vault semantics: filesystem, index, addresses, reading/editing Typst syntax (it depends on `typst-syntax`, not `sliver-typst`). `sliver-typst` also uses `typst-ide` (jumps; later completion). Don't add more crates without asking first.
- **Editor (M4):** CodeMirror extensions live in `src/editor/`.
  - Highlighting and wikilink ranges come from the native `analyze` command (`sliver-vault/syntax.rs`, `typst-syntax`'s `highlight` tags as `typ-*` classes coloured by `--syn-*` tokens), not the compiler: it never waits behind a compile. At most one request is in flight, always for the latest text; results for older text are dropped and the previous decorations are mapped through edits meanwhile.
  - Wikilinks show as their target's title, or its address when the `linkDisplay` setting says so and the note has one, like the preview (custom text always wins; red when broken; the hover shows the other form), until the cursor enters them, then as source. A uuid never shows in the editor, and the file isn't edited to hide it: the editor's text is a view over the file (`linkView.ts`). It has the note's title where the file has `[[uuid]]`, and a table (`uuidLinks`, mapped through edits, restored by undo and redo through `invertedEffects`) remembers which uuid each title stands for while its text is unchanged. Text converts only where it crosses: `fromFile` when a note opens and `reloadSpec` for a reload from disk (both only for the link ranges `analyze` reports, so `[[uuid]]` in raw text or a comment stays as written; the incoming filter skips raw likewise), `toFile`/`savedText` for saving, and a transaction filter for text coming in (a uuid from a completion, a retarget or a paste becomes its title in the same transaction; a complete link pasted or put in at once whose title names a note links to it). Copying copies titles; uuids never reach the clipboard. When a linked note is renamed, open notes update the title text (`renamedTitles`, on every tree change): a real edit, an undo step of its own, since a change kept out of history would make history map other steps through it and corrupt them. Positions crossing to the compiler (diagnostics, preview clicks, cursor follow) are mapped between the two (`fileToDocPosition`, `docToFilePosition`); completion, signature help and hover run on the editor's text. Entering and leaving a link changes nothing; leaving one whose text was edited resolves it (`leave`): a note's title links to it (its address, or an entry for its uuid, an undo step of its own), an address or uuid stays, anything else stays an uninitialized link. Nothing is resolved after undo or redo. Cmd/Ctrl-click follows the link in place, Cmd/Ctrl+Shift-click in a new tab. Typing `[[` (outside raw) opens an autocomplete menu of all notes that inserts `address]]`, or a uuid (shown as the title) for unaddressed notes (`linkTarget`).
  - While a link's target is typed, no completion source asks again per key (the link source updates its result in place, `update`; the others hold an empty one, `quietInLink`): a source asking again disables the open menu until it answers, and Enter meanwhile typed a newline.
  - The `[[` menu's last option, "New note", is pinned below the list as a footer (`menuChrome`, since CodeMirror renders only a window of the options; the footer takes the option's id so clicks and selection still work). It asks for a title (starting from the typed text) and a folder (`newLinkedNote`), creates the note without opening it, keeps focus in the linking note, and fills the link in once the note exists (`pendingLinks` tracks the link's range through edits meanwhile; nothing happens if its text was deleted).
  - Undo is CodeMirror's `history()` in both modes (Vim's `u`/Ctrl-r run the same commands, then put the cursor at the change's start; Mod+Z restores the selection instead). Grouping is time-based in both, not per Vim insert session (the user's choice). Every accepted completion is an undo step of its own (`ownUndoStep`: `isolateHistory` on `input.complete`), so text typed right after it undoes separately.
  - Autocomplete (`@codemirror/autocomplete`, `src/editor/completion.ts`) has three sources: wikilink targets after `[[`, citation keys from the whole Zotero library after `@` (Better BibTeX `item.search` through `zotero_search`, at least two characters, only items `references.bib` lacks since Typst offers those; none while Zotero is closed; citing one fetches its entry on the next save), and Typst completions from `typst-ide` in the engine (`complete`, run on the editor's current text without touching the engine's copy, so compiles and diagnostics stay consistent). Typst's `${field}` snippets go through CodeMirror's `snippet()` with a literal `#{` escaped. Completion icons are Lucide icons (`addToOptions`), not CodeMirror's text glyphs.
  - Signature help (`signature.ts`, engine `signature`): once `(` is typed, or on "Show parameter hints" (Mod+Shift+Space; Ctrl+Space is CodeMirror's completion), and then for as long as the cursor stays in that call (Escape, blur or leaving the call end it), a tooltip shows the function's parameters with their types, bolds the one at the cursor (by name for named arguments, else by position) and shows its docs (or the function's). The callee is resolved by tracing, falling back to the standard library while the call doesn't evaluate yet. Engine analysis (completion, signature) runs on the editor's text through an overlay source in the world, never the engine's stored copy.
  - Hover tooltips (`hover.ts`, engine `tooltip`): `typst-ide`'s tooltip for what's under the pointer (a value as code, or the first paragraph of a function's or parameter's docs), run on the editor's text like completion; not over wikilinks and citations, which have their own.
  - Formatting (`format.ts`, commands `format.bold` Mod+B and `format.italic` Mod+I): wrap each selection in `*`/`_`, or unwrap it when it's wrapped (inside or just outside the selection); an empty selection gets an empty pair, or loses the one it's in.
  - Vim ex commands (`vimCommands.ts`): `:w` saves, and `:q`, `:wq` and `:x` close the note's tab (saving first, like every tab close). Ex commands are global to the page, so each editor registers its own actions (`setVimActions`); the settings view's preamble editor only has `:w`.
  - Auto-closing pairs (`brackets.ts`): `( [ { " $` and backticks, not `'` (an apostrophe in prose).
  - Squiggles and hover messages are our own `StateField` + `hoverTooltip` (no `@codemirror/lint`). Only the note's own diagnostics are shown, and only when the compiled text equals the document; otherwise the old ones follow the edits.
  - Preview ↔ source sync uses `typst-ide` in the engine, which keeps each main file's last good `PagedDocument`. A click on a preview page (not on a link) moves the editor's cursor there; when the cursor rests for 150 ms after a move (not typing), the preview scrolls to it if it's off-screen and flashes a marker (setting `previewFollowsCursor`, on by default).
  - "Toggle debug view (compile timings)" shows the visible note's compile and render times (measured in the engine), the rest of the backend command (waiting for the compiler, replacing the source), the DOM work of applying the result, edit-to-preview round trip (including that DOM work) and syntax-analysis round trip, with the recent maximum and a bar per compile.
- **Startup** (measured: harness, vaults of 2,000 and 10,000 notes). Opening a vault fetches settings, then the links rule, preambles, theme and citations together while the open tabs load; a note's first compile waits only for those to reach the compiler (`vaultSources`). The `references.bib` parse check runs after the first previews (`checkDeferredReferences`), assuming it's fine until then. `Vault::open` walks the folders, then reads and parses the notes on every core (`parse_all`, plain threads): 2,000 notes in about 50 ms (release) and 280 ms (dev), 10,000 in 230 ms and 1.4 s. Folded sidebar branches render nothing until unfolded; an unfolded folder still renders every row (10,000 rows add about 1.8 s; see M10).
- **Compiling:** one long-lived `Engine` in the backend holds every open note, compiled per tab (`compile(main, render)`); `comemo` caches the work (`evict(10)` after each compile). At most one compile is in flight per tab, and edits made meanwhile collapse into one follow-up compile (`livePreview`, which sends the new source with the compile request, one call). Diagnostics use 0-based lines and UTF-16 columns. Fonts are the embedded `typst-assets` set only so far.
  - Only what's on screen renders: a note whose preview isn't shown (`visibleNotes`) compiles after a 400 ms pause and without rendering pages (its diagnostics still feed the editor's squiggles), and is marked stale until shown. Pages render in **bands** (`bands.rs`): a preview page is as tall as its note, so the engine cuts each laid-out page (the `Frame`, not the SVG) into horizontal bands of at least 400 pt and renders each as its own SVG. Cuts go only where no content crosses, and where depends on the content after the cut (a hash), so an edit only changes the bands around it and the cuts after it stay put. Each band has a key, a hash of what it draws, ignoring source spans and introspection locations (an edit renumbers those in everything after it) and with positions rounded. The engine renders (and sends) only bands whose key wasn't in the main file's last render; the frontend reuses the rest by key. In the preview each page is a box sized by its aspect ratio with its fill (`background`) and its bands positioned in percent, and only bands within half a viewport of the visible area have their SVG in the DOM (`showNearBands`, on scroll and resize). So the DOM work of a compile is a few screens of SVG whatever the note's length: a width change on a 21,000 px note went from about 565 ms to about 50 ms on the main thread. Band SVGs don't clip (`overflow: visible`), since text extents come from font metrics and a big glyph may overhang. `page_svgs` renders whole pages for small throwaway mains (the citation card).
  - Changes recompile only what they affect: links, theme and preamble changes recompile visible previews now and mark the rest stale; a preamble save reloads only the notes whose last compile read it (`affectedMains`).
  - Closing a note removes everything the engine holds for it: its text, prefix, wrapper (with the last layout, dependencies and page hashes) and page file.
- **Compiler host** (`src-tauri/src/compiler.rs`): the engine runs natively in the backend, not as WebAssembly in a worker (measured about 1.5-2.5x faster per compile, much less in the slow tail, and no 38 MB WebAssembly to load at startup; multiple cores didn't help these notes). One `Engine` behind a mutex, created on a thread at startup (`warm_up`; the embedded fonts are parsed once per process, `EMBEDDED_FONTS`, so a rebuild reuses them); every `typst_*` command runs on `spawn_blocking`, one at a time. The frontend's `TypstClient` (`typst/client.ts`) keeps the same API it had over the worker. A compile comes back as one raw body (`Response`): a little-endian `u32` header length, a JSON header (pages, bands with each SVG's end offset, diagnostics, anchor, missing packages, timings), then the new bands' SVG as UTF-8 bytes back to back, decoded per band in the client; other results are JSON, with null fields left out (`compact`) so JS sees them as missing. A panic inside Typst is caught (`catch_unwind`; the release profile unwinds, not aborts, for this) and the engine is rebuilt from every input it was given (sources, prefixes, files, packages, kept by the host), so the next call works; the failed call returns an error. In `tauri dev` dependencies and `sliver-typst` build with `opt-level = 3` (`[profile.dev.package]`), since a debug build of Typst is far too slow to preview with.
- **Packages** (optimized for latency): the engine reports `missingPackages`; the client (`TypstClient.ensurePackages`, in the webview, so no TLS stack is needed natively) asks the vault cache (`load_package`), else fetches `packages.typst.org`, gunzips with `DecompressionStream`, hands the tar to the engine (`typst_add_package`, a raw body) and has the waiting previews recompile (`onLoaded`), then caches the download via `save_package` off the critical path. Failed specs retry after 30 s, and "not found" errors show as a "Downloading ..." notice. With no vault open, packages live only in the engine's memory.
- **Panes** (`src/state/layout.ts`, `Workspace.tsx`): the editor area is a tree of splits (`row`/`column`, nested any which way, flex weights resized by our own `Divider`) whose leaves are panes. A pane is the unit: its own tab bar, its active note's editor and, in per-pane preview layout, that note's preview, in one frame, so layout shows which preview belongs to which editor. The focused pane (last clicked or typed in) is where commands and `openNote` act; only its active tab carries the accent.
  - Tabs are editor-style containers (custom `TabBar`, not Ark `Tabs`): Mod+T (or the + after the tabs) opens an empty tab. Opening a note (sidebar click, note switcher, following a link) replaces the note in the current tab, as in Obsidian and browsers, so jumping around doesn't pile up tabs: `openNoteHere` (the focused pane) and `followFrom` (a link: the pane showing the linking note, which from the global preview column isn't the focused one) go through `navigate`, which flushes the replaced note's edits first; back returns to it. A modifier opens a new tab instead (`openNote`: fills the focused pane's active empty tab, else a new one): Cmd/Ctrl-click or middle-click in the sidebar, Mod+Enter in the note switcher (`runAlt`, hinted under the list), Cmd/Ctrl+Shift-click on a link in the editor, Cmd/Ctrl-click on one in the preview, Mod+Shift+Enter ("Follow link at cursor in new tab"). Either way a note already in a tab is activated there. Replacing a note discards its editor, so its undo history and cursor go (accepted). New notes still open in a new tab. A note is in at most one tab across all panes. Dragging a tab within its bar reorders; dragging it off onto a pane drops it into that pane (centre or tab bar) or splits it off on that side (an edge), with an overlay showing where. A pane left without tabs disappears (never the last one). Commands: split right/down (Mod+\\, Mod+Shift+\\), focus next/previous pane, close pane.
  - Editors live outside the pane tree (`editorHosts.tsx`: one Solid root per open note) and panes adopt their elements, so splitting and moving tabs never remount an editor: inactive tabs keep their cursor and undo history.
  - Navigation (`state/navigation.ts`, buttons at the left of each pane's tab bar, and commands): back and forward through the notes the pane's active tab showed (per tab, like a browser's, keyed by tab so it moves with a dragged tab, dropped when the tab closes, not persisted; going to a note open in another tab activates that tab and leaves this one's history alone; Mod+[ and Mod+], which take over CodeMirror's indent less/more), and along the Folgezettel: parent (the nearest existing ancestor), first next note (first child), previous and next aside (siblings); Zettelkasten notes only, commands unbound by default. Moves replace the pane's active note (`navigate`, like a browser tab) instead of opening tabs; a note already open in a tab is activated there.
  - View modes per pane: editing (editor and preview), reading (preview only, Mod+E; clicks in it never move or show the editor, only links act) and source (editor only; "Toggle preview", Mod+Shift+P). A new pane (from a split, or an empty workspace) starts in the `defaultViewMode` setting. Preview layout (`previewLayout`, "Toggle global preview mode"): one preview per pane, or global: one shared column showing the note of the last focused pane not in reading mode (there Mod+Shift+P hides the column; it also goes away while it has no note to show, e.g. every pane is in reading view). The layout, focused pane and sizes persist in `workspace.json`.
  - Each tab autosaves after a pause (`autosave`, `autosaveDelay` settings); with autosave off it saves on Mod+S. Either way pending edits are flushed on tab close, window close, and before renames and moves, so nothing is lost silently.
- **Commands:** every user action is a command in the registry (`src/commands/registry.ts`, `Mod` = Cmd on macOS, Ctrl elsewhere). The palette (Mod+P) and note switcher (Mod+O) list them; keybinding hints render through `Keys` (one spaced span per key, system UI font); keybindings are dispatched in the capture phase, before the editor, and are off while a modal dialog (settings, palette, prompt) is open. Each command has a default keybinding; the vault's `keybindings` setting overrides them by command id (`""` for none), edited in the settings' Keybindings section (click a binding, press keys; it notes clashes). Vim: in a Vim editor, a default binding that is Ctrl with a letter Vim uses (`vimUses`: scrolling, jumps, insert-mode editing) goes to Vim, so on Windows and Linux Ctrl+P, Ctrl+O and the like stay Vim's there; a binding set in the settings takes the keys over. Context-menu commands (`contextMenu`) have no keybindings.
- **Settings** are per vault, in `.sliver/settings.json` (`load_settings`/`save_settings`), so vaults can have different workflows; the schema and defaults are frontend-owned in `src/state/settings.ts`, and the settings dialog needs an open vault and has "Restore defaults" (`restoreDefaults`). Only the last vault (`<app config dir>/state.json`) and window geometry are app-level.
- **Preambles** (`preambles.rs`): shared Typst code in `.sliver/preambles/`. `common.typ` applies to every note (a vault without one gets the default: 12pt margins and text, more space below level-one headings); `kinds/<kind>.typ` applies to notes whose header says `kind: "<kind>"`. The kinds are the files (`Vault::kinds`); a kind is optional, and a note whose kind has no file gets a sidebar warning and only the common preamble. Edited in the settings view ("Templates", with the note templates), saved when typing pauses (always, there's no Mod+S there) and when the editor closes.
  - Names reach a note through hidden `#import "<preamble>": *` lines the engine compiles before the note's text (`note_prefix`, `Engine::set_prefix`): whole lines, so the engine translates positions by a line count at its API boundary (diagnostics, jumps, completion, signature help); a diagnostic inside the prefix maps to the note's start. Notes that use preamble names don't compile outside the app; accepted.
  - Styles reach a note through the preamble's `template(body)` function, which the wrapper main applies with `#show:` (common, then the kind) inside the theme's defaults; the preview's page width and height are applied after them, so a preamble can't break the fit to the pane. Set rules inside an imported module never reach the importer, so a preamble's top level holds definitions only (imports, `let`): `preamble_warnings` flags top-level set/show rules, content and relative paths, since exporting a note inlines its preambles and those would then behave differently.
  - Compiled once: Typst's `comemo` memoizes module evaluation, and every note compiles in the one long-lived engine, so a preamble (and its packages) is evaluated once per change and reused by every note and edit; only each note's layout reruns.
  - "New note of kind" (Mod+Shift+N) asks for a kind and uses its default folder (`kindFolders` setting) if it has one, else where Mod+N would go; "Change kind" sets or clears it (`set_kind`). Renaming a kind rewrites the `kind` of its notes; deleting one leaves them with a warning. Errors in a preamble show in every affected preview, labelled with the preamble.
- **Note templates** (`state/templates.ts`, `.sliver/templates/`): what a new note starts with below its header, unlike preambles, which are compiled with it and never in it. The default template, or the note's kind's if it has a non-blank one (`note_template`). A new vault starts with the default template `= {{title}}`, a blank line and `{{cursor}}` (`DEFAULT_TEMPLATE`); an existing vault without one gets none, and "Restore defaults" leaves templates and preambles alone (they're files, not settings; its dialog says so). Each preamble and template has its own "Restore default" in the Templates section (`default_text`: the starter preamble, `DEFAULT_TEMPLATE` for the common template, empty for a kind's). Placeholders are filled in by the frontend when the note is created and passed to `create_note` as its `body`: `{{title}}` (escaped for markup), `{{date}}` and `{{time}}` (`YYYY-MM-DD`, `HH:mm`), and `{{date:FORMAT}}`/`{{time:FORMAT}}` with Moment-style tokens as in Obsidian (`formatDate`; `[text]` literal). `{{cursor}}` marks where the new note's editor puts the cursor (the first one; leading blank lines are dropped, trailing ones are kept down to the cursor's line), and the editor takes focus. Edited in the settings' "Templates" section (a Preamble/Template switch per entry); renaming or deleting a kind renames or deletes its template too.
- **Citations** (`citations.rs`, `src-tauri/src/zotero.rs`, `src/state/citations.ts`): `@citationKey` (Typst's own reference syntax, so `@key[p. 7]` and side-by-side grouping come free; `#cite(<key>, ...)` also works), with Better BibTeX citation keys from the user's Zotero library. Better BibTeX is required: it provides the keys, the picker and the export.
  - `.sliver/references.bib` holds BibLaTeX entries only for keys the vault cites (the index keeps each note's keys from the syntax tree; a reference to a label defined in the same note is a cross-reference, not a citation). It's fetched with Better BibTeX's JSON-RPC `item.export` (an unknown key fails a whole export, so each one named is dropped and the rest retried) and merged in (`merge_references`, dropping the machine-specific `file` field). Refreshed in the background on vault open (all cited keys, pruning uncited entries), after each save that cites a key without an entry, after picking, and by "Refresh references from Zotero". Zotero being closed only means nothing new is fetched; previews use the vault's copy. HTTP is `ureq`, off the async runtime, with the vault unlocked meanwhile.
  - The preview never fails over a citation: the wrapper gets the known keys from the generated `/.sliver/citations.typ` (`citation_library`), and `show ref`/`show cite` rules draw a reference that is neither a label nor a known key as red `@key` (Typst only errors when it draws the reference itself). Known citations become `sliver-cite:<key>` links (`link(..., it)` keeps grouping), but Typst also links a citation's text to its bibliography entry, which SVG can't express (anchors without an href), and a group links only to its first key. So the preview finds what's under the pointer by position instead: the run of touching link areas on the line, and the engine's `citation_marks` (where each cite starts; Typst puts the others of a merged group at its end; cross-references are marks without a key). A click on several asks which to open. `references.bib` is checked to parse before use; if it doesn't, the wrapper leaves the bibliography out and the preview shows a notice. The reference list shows only when the note cites a known entry (setting `showReferences`).
  - Style: the vault's `citationStyle` (a Typst style name or a `.sliver/styles/*.csl` path), then a kind template's `set bibliography(style: ...)`, then the note's `citation-style` header field (read in the wrapper with `query(<note>)`, so it applies while typing). A header naming an unknown style shows a notice and keeps the default, because an unknown style would fail the compile; the valid names come from the engine (`citation_styles`, Typst's own list). The wrapper records the style used as `<sliver-citation-style>` metadata.
  - Details: hovering a citation (editor or preview) shows each entry rendered by Typst in the note's style (a throwaway main per entry, `standalone`, cached until references, style or theme change) with "Open in Zotero" (`zotero://select/library/items/<item key>`, the item looked up by citation key with Better BibTeX's `item.search`, opened through `tauri-plugin-opener`); unknown keys say whether Zotero is reachable. Mod-click in the editor and a click in the preview open the item in Zotero. "Insert citation from Zotero" (Mod+Shift+C) opens Better BibTeX's picker (`cayw?format=json`), saves the picks' entries, refocuses the window and inserts `@key`, `@key[p. 7]`, or `#cite(label("key"), form: "year")` when the author is suppressed. `@` completion comes from Typst itself for keys in the bibliography, and from the Zotero library for the rest (see Editor).
- **New notes (Mod+N)** go where the vault's settings say, as in Obsidian: `newNoteLocation` is the vault root, the current note's folder, or `newNoteFolder` (picked by fuzzy search, Ark `Combobox`). A missing folder falls back to the root. Mod+N (and "New note of kind" for a kind without a default folder) asks for the title and the folder in one dialog (`promptWithChoice`: `prompt` plus an "In:" dropdown starting at that folder, with a `validate` callback for inline errors), as does creating a note from the `[[` menu. A note landing in the Zettelkasten asks for its address first (new top-level, or next note / aside of a chosen note).
- **Theme:** the per-vault `theme` setting ("system" by default, "light", "dark") sets `data-theme` on `<html>` (dark colours live under `:root[data-theme="dark"]`) and the native window theme (`src/state/theme.ts`). Previews have their own `previewTheme` ("app", "light", "dark"; `isPreviewDark`), which picks the `theme.typ` the compiler gets and the page colour (`--paper` under `.preview[data-preview-theme]`); the pane around the page and the diagnostics stay in the app theme. Startup doesn't flash: the backend creates the window itself (`window.rs`, not `tauri.conf.json`) with the last vault's theme, read from its `settings.json`, as the native theme and background, and an initialization script hands it to the page as `window.__SLIVER_THEME__`; an inline script in `index.html` sets `data-theme` from it before the first paint, and the settings start with it until the vault's own load (`resetSettings` keeps the theme, since a vault opens right after). The page shows a spinner (`#startup` in `index.html`) while the app mounts hidden; it fades in once the previews on screen have their first pages (`firstPreviews`: pages, or a failed compile with no packages or files still loading; 3 s at most).
- **Preview theming** (light/dark): `/.sliver/theme.typ` (`theme_library`, `theme.rs`) names the theme's colours (`ink`, `paper`, `muted`, `accent`, `error`, `warning`, `rule`, plus `light` and `untheme`). The vault writes the light version to disk on open, so notes that import it (`#import "/.sliver/theme.typ": accent`) still compile outside the app with the vault as root and export light; the compiler gets the current theme's version, and a theme change recompiles the visible preview (others when shown). The preview wrapper applies it as defaults (page fill, text, lines, tables, links in `accent`, broken wikilinks in `error`). Opt-outs: `theme: false` in a note's header (shown as on light paper; the wrapper reads it with `query(<note>)`, so no Rust round trip) and `#untheme[...]` for one element. The palettes in `theme.rs` mirror the CSS colour tokens; keep them in sync.
- **Preview page:** the wrapper sets `width: page-width, height: auto` (`page-width` from the note's own generated `/.sliver/page/<id>.typ`, `page_path`, since previews side by side differ in width), so a note is one page as wide as its preview: never `width: auto`, which never wraps text. The width is capped by the `maxPreviewWidth` setting (560 px by default, about 75 characters a line) and snapped to 6 pt steps; a newly opened note starts at the last width set. While the layout is being resized (a divider or the sidebar dragged, or the window resized within the last 200 ms; `resizing` in `workspace.ts`), CSS stretches the old page and nothing compiles; when it ends, each changed preview recompiles once at its final width, only that note, through `livePreview`'s collapsing. (With bands, compiling live during a drag also works without stalling, at the cost of a hitch per compile landing and a busy compiler; removing the `resizing` check in `Preview.tsx` switches to that.) The preview anchors its scroll position to the point at the top of the visible area (`measureAnchor`/`restoreAnchor` in `Preview.tsx`): when the pages change size it stays put on screen, through CSS stretching (uniform, so exact) and through reflows, where each compile carries the anchor (`compile_anchored`) and the engine finds the text at or below it again in the new layout by its glyph's source span (identical across a width change), returning its new position, applied before the next paint. Previews off screen that went stale (theme, preambles) recompile when shown (`visibleNotes`). Page setup stays out of note files so a future export can pick its own page.
- **Preview text and links:** Typst's SVG draws glyphs as outlines, so each band's SVG gets an invisible text layer (`text_layer.rs`: one transparent `<text>` per text run at its baseline, stretched with `textLength` to the run's width, like PDF.js), which makes the preview's text selectable with the webview's own highlight. Copy is ours (`selectedText`): the selection's part of each run, a line break where the baseline changes. The layer lies over the links, so links are found by position (`anchorAt`, `elementsFromPoint`) for clicks and hover, not from the event target. A drag that selected text doesn't move the editor's cursor. Only bands near the viewport are in the DOM, so a selection can't reach far beyond the screen. `http(s):` and `mailto:` links open in the default browser or mail app (`open_url`, which allows nothing else).
- **Window geometry** (size, position, maximized) is per machine, so it never goes in `workspace.json` (a synced vault would carry one machine's monitor layout to another). `tauri-plugin-window-state` keeps it in the app config dir.
- **macOS menu:** Tauri's default minus "Close Window", so Cmd+W reaches the webview and closes a tab. The Edit menu must stay: macOS routes copy/paste/undo through it. Quit is our own item (`menu.rs`): the standard one terminates at once, so ours emits `quit-requested`, the webview flushes every note and calls `quit`, and after 5 s the app quits anyway. Quitting from the Dock or at logout still skips the flush (autosave limits the loss).
- **Dependencies:** keep them minimal.
  - UI: Ark UI (`@ark-ui/solid`, imported from the package root): Splitter, TreeView, Menu, Dialog, Switch, Combobox (the settings folder picker). The palette is `Dialog` plus our own combobox list (Ark `Combobox` is a floating dropdown).
  - Editor: CodeMirror 6 core packages plus `@codemirror/autocomplete` and `@replit/codemirror-vim`.
  - Icons: Lucide (`lucide-solid`). Import each icon by path (`import Plus from "lucide-solid/icons/plus"`); use the canonical names from `dist/types/icons/`.
  - Tauri plugins: `tauri-plugin-dialog` (native dialogs), `tauri-plugin-window-state` and `tauri-plugin-opener` (both Rust side only; no JS package or capability).
  - HTTP to Zotero's local endpoints: `ureq` (no TLS, `json` feature).
  - File watching: `notify-debouncer-full` (re-exports `notify`).
  - Sync: `iroh` (optional, feature `sync`; `tokio` and `data-encoding` come with it), and in `sliver-vault` `diffy` (three-way merge), `blake3` (content hashes) and `serde_json`.

## Roadmap

### M5 — Panes

Built (see Panes under Decisions); still to do:

- [ ] Focus the pane in a direction (left/right/up/down) rather than only next/previous
- [ ] Multiple main windows (Later) reuse this: a window is a pane tree

### M6 — Commands & keybindings

- [ ] Fill out the native menus: the macOS menu bar, and the window menu bar on Windows and Linux. Items come from the command registry (File: new note, new tab, open vault, settings; Edit: undo, copy, paste, formatting; View: toggle preview, debug view; Go: switch note, next and previous tab), with their keybindings shown as accelerators. The macOS Edit menu stays, since copy, paste and undo go through it.

### M7 — Search

All in memory and computed from the note files, like the rest of the index (no database). Indexing happens in `sliver-vault` (native) on open and on every write.

- [ ] Full-text index: each note's text as a reader sees it, taken from the syntax tree (markup text, headings, raw; not code, the header or wikilink targets), stored with source offsets so a hit can open the editor at the right spot
- [ ] Search view in the sidebar: results grouped by note with highlighted snippets; clicking a hit opens the note (in the focused pane) at that place. Live as you type, after a short pause
- [ ] Query syntax: words and `"phrases"`, plus filters `tag:`, `kind:`, `folder:`, `address:` (a prefix, for a train of thought: `address:1.1`), `links:<target>` (notes linking to it), and negation (`-tag:draft`)
- [ ] Search inside the current note (CodeMirror's search panel; Vim's `/` already works)
- [ ] Note switcher (Mod+O) also matches tags and kinds, not only titles and addresses
- [ ] Later, maybe: replace across the vault (with a confirmation listing the changes, like moves), and saved searches

### M9 — Peer-to-peer sync

Built behind the `sync` feature (see Sync under Decisions); still to do:

- [ ] Try it across networks: connect time, direct vs relayed, and decide when the feature becomes default
- [ ] A setting for a self-hosted relay (and whether to drop n0's address lookup with it)
- [ ] Trust across devices: devices paired with the same device learn of each other, so a phone and a laptop paired only with a desktop sync directly
- [ ] Pairing into an existing vault (both sides populated); today only an empty folder can join
- [ ] Large assets: stream them instead of holding a whole file in memory per round
- [ ] Later, maybe: sharing a vault with another person (read-only or read-write tickets)

### M10 — Large vaults

- [ ] Virtual scrolling in the sidebar: render only the rows on screen (a flat list of the visible rows of the tree), so a folder or train of thought with thousands of notes unfolds instantly. Ark's TreeView renders every row, so this means our own tree list (keyboard navigation, folding, selection, context menu, dragging)

### M11 — System fonts

- [ ] System fonts: the backend discovers them, and the engine loads a font's bytes only when a compile needs that font (now direct file reads, since the engine is native)

### M12 — Export

Not a priority. Keep page setup and theme out of note files so this stays possible.

- [ ] PDF (and other formats) through an export wrapper of its own: a fixed or chosen page size, the light theme, and the note's preamble templates applied
- [ ] Standalone `.typ` export: the hidden preamble imports replaced by the preambles' source inlined (common first), followed by their `#show: template` lines
- [ ] Citations: copy `references.bib` (or the cited part) next to an exported note, with the export wrapper's `bibliography` call
- [ ] Wikilinks in an export: as plain text, or `#link`s (to sections, once section links exist)

### M13 — Onboarding

- [ ] "Open tutorial vault" on the welcome screen: a vault copied from files shipped with the app into a temporary directory, so nothing persists. It's deleted when the app closes or another vault opens, never recorded as the last vault (`state.json`), and shows a notice that it's temporary
- [ ] "Keep tutorial vault…" (only while the tutorial vault is open): copies it to a folder the user picks and opens it from there as an ordinary vault. Closing the app (window close or Quit) with the tutorial vault open asks whether to keep it first (keep, discard, cancel), as does opening another vault
- [ ] Tutorial content as notes in the vault itself: the Zettelkasten and addresses (next notes and asides), wikilinks and backlinks, Folgezettel navigation, folders and the Inbox, kinds, preambles and templates, citations with Zotero, the palette and keybindings
- [ ] Empty states that teach: an empty vault, an empty Zettelkasten and an empty tab each say what to do next, with the relevant keybindings
- [ ] A keybinding overview (a palette command or settings link), and first-run hints in a new vault, e.g. a starter note that links to the tutorial

### M14 — Outlines

Compose notes (Zettelkasten or any folder) into larger structures, as Luhmann's structure notes did: an outline orders and nests notes for a project, an article or a topic, and a note can be in any number of outlines. Nothing about a note changes when it joins an outline.

- [ ] Format: an outline is itself a note, marked by a header field (`outline: true`; additive, no break), so it lives in a folder, has a title and can be linked, synced and moved like any note. Its body is a Typst list, nested for structure: an item that is a wikilink (`- [[1.1a]]`, `- [[1.1a|custom heading]]`) places that note, any other item is a section heading of its own, and text after an item's link is a comment. Parsed from the syntax tree (`typst-syntax`, like `links_in`) into the index; no new files, no database. An outline item can be another outline (nesting), with cycles flagged as warnings
- [ ] Membership: "in outlines" for each note comes from the index, like backlinks (shown wherever backlinks are, and as a count in the note's tooltip); moves and re-addressing already rewrite the links, so outlines follow their notes
- [ ] Outline view: a tab showing the outline as a tree (titles and addresses, warnings for broken links), editable by dragging rows to reorder and indent, dragging notes in from the sidebar, "Add to outline..." on a note (pick an outline and a place) and removing items. Every edit rewrites the list in the outline's source through `typst-syntax` so the user's other text and comments stay byte for byte; the source stays editable as a normal note too
- [ ] Reading an outline: a preview that renders the notes in order as one document, each note's heading levels offset by its depth (`set heading(offset: ...)`), with each section linking back to its note. Needs a transclusion wrapper: notes keep their own hidden preamble prefixes and kind templates (the engine already keeps a prefix per path), and their `<note>` header metadata must not confuse the wrapper's `query(<note>)`. Compiles only the visible part, like bands
- [ ] Creating: "New outline", and "Outline from train of thought" (a Zettelkasten note and the notes under it, in address order, as a starting outline to rearrange)
- [ ] Export (with M12): an outline exports as one PDF or a standalone `.typ` with every note inlined
- Open questions: whether an outline item can pick part of a note (a section, once section links exist); whether outlines get their own place in the sidebar (a filter or a section) or stay ordinary notes found through the switcher; how a note's title shows in an outline versus a custom heading in the item

### Later

- Multiple main windows on the same vault, e.g. for two monitors, each with its own tabs, panes and preview. Each window is a separate webview, so its JS state is its own (the native compiler could be shared, or one per window). The backend's `Vault` stays the single owner of the files. Open questions:
  - whether a note may be open in two windows at once (today a note is in at most one tab), and if so, how edits stay in sync;
  - how `workspace.json` records several windows' tabs and layout;
  - how a change made in one window reaches the others (settings, preambles, the tree after saves and moves): backend events that every window listens to, which settings would then use too.

### Open questions

- User-defined note properties: should extra header fields (e.g. `status: "draft"`, `source: "..."`) be indexed, so search filters, the sidebar and a properties view can use them? Today they're allowed and kept byte for byte, but ignored by the index
- Section links `[[target#heading]]`

## Findings to revisit

From a review (2026-11-05) of how the features interact and where time goes; not acted on yet.

- **A title change refetches the whole sidebar tree** (about 440 KB at 2,000 notes); the backend could send just the changed note's summary.
- **Each save syncs the file to disk** (`fsync`, about 5 ms); fine for autosave, but moves that rewrite links in many notes pay it per file.
- **A `kind:` typed into the header applies only after the next save**: the hidden import and wrapper come from the saved index, not the editor's text.
- **"Change kind" writes the note twice**: the command writes the file, then the editor's `replaceText` triggers an autosave of the same text.
- **Vim's `.` repeat replays non-typed changes as typed text**: the CM6 adapter reports every change in insert mode without an origin, so completions and link resolutions land in the `.` register.
- **Showing or hiding the global preview column rebuilds the pane area**, so pane previews lose their scroll position (editors are hosted outside and keep theirs).

## Gotchas

- Don't use a component's return value as a DOM node (`<Foo /> as HTMLElement`): in dev, hot reloading wraps it in a function. To render outside the tree, `render()` into an element you create (as `editorHosts.tsx` does).
- Ark renders some parts as `<button>` (splitter handles, `Menu.ContextTrigger`, `TreeView.BranchTrigger`). Base button styles are scoped with `button:where(:not([data-scope]))`, and a container that must not centre its content uses `asChild` with a `div`.
- HTML5 drag and drop is unreliable in the Tauri webview (Tauri's file-drop handling intercepts it). Use pointer events, as `TabBar` does.
- WebKit needs `-webkit-user-select` alongside `user-select`.
- Lucide 1.x renamed some icons (e.g. `trash-2` → `trash`, `triangle-alert` → `triangle-exclamation-point`); the old paths load but have no types.
- Typst's SVG export draws text as glyph outlines, so you can't grep rendered SVG for text; links appear as `<a href>` over a transparent `<rect>`, and links to places in the document (a citation's text, `@heading` references) as `<a>` without an href.
- CodeMirror tooltips render into a fixed `.tooltip-layer` with no height but the window's width (narrower, tooltips shrink to their narrowest) in the body (`tooltips({ parent })` in `Editor.tsx`), since the panes clip their content. Not into the body directly: each editor's container carries its theme classes (so `height: 100%`), which made the body scrollable and anything scrolled into view shifted the whole app up.

## Environment

- Nix flake dev shell (`flake.nix`, loaded by direnv via `.envrc`) provides stable Rust and pnpm. Run tools inside it. From a non-direnv shell, prefer `source .direnv/flake-profile-*.rc` over calling `nix develop -c` per command, since each flake evaluation after a change copies the tracked tree into `/nix/store`.
- Git: read-only for Claude. Never commit, stage or otherwise change git state.
- Package manager is **pnpm** (`pnpm-lock.yaml`); don't use npm/yarn.

## Commands

- `pnpm install` — install JS deps
- `pnpm tauri dev` — run the desktop app (starts Vite on fixed port 1420, then the Rust app); `pnpm tauri dev --features sync` with sync
- `pnpm tauri build` — production bundle (runs `pnpm build` → `dist/`)
- `pnpm dev` — Vite only (no backend, so no compiler or vault)
- `pnpm check` — everything CI-worthy: `biome check`, `tsc --noEmit`, `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test` (run before calling work done)
- `pnpm format` — `biome format --write` + `cargo fmt --all`
- `pnpm lint` — Biome lint, `tsc`, clippy; `pnpm test` — `cargo test --workspace`
- `cargo test --release -p sliver-vault --test perf -- --ignored --nocapture` — timings of the vault's hot paths (open, tree, refresh, link tables, resolve, writes) on generated 2,000- and 10,000-note vaults

## Conventions

- Frontend → backend: `invoke("command_name", { args })` from `@tauri-apps/api/core`, matched by a `#[tauri::command]` fn registered in `lib.rs` (arg names are camelCase on the JS side).
- Solid, not React: use `createSignal`/`createResource`, `class` not `className`; components run once (don't destructure props).
- TypeScript is `strict` with `noUnusedLocals`/`noUnusedParameters`.
- Vite ignores `src-tauri/**`, `crates/**` and `target/**` for watching; Rust changes are rebuilt by `tauri dev`.
- Keep dependencies minimal. Before adding any new crate or npm package, give a strong justification and ask the user first; never install one unprompted.
- Limit comments to things that wouldn't be obvious to an experienced developer.
- Avoid emoji in code.
- Personal vaults are off limits: never read, list, open, copy or benchmark against any user's or developer's own vault (nor follow `state.json` to one). Use generated or mocked vaults.
- Breaking changes need approval: real vaults exist now, so before any change that would break existing vaults or on-disk data (layout, header fields, `.sliver/` files, `workspace.json`, settings), say what breaks and ask first. Don't write migration or compatibility code unless asked.
- Scrollbars are overlays: native ones are hidden app-wide, and every scroll container gets floating, auto-hiding thumbs from `components/scrollbars.ts` (`overlayScrollbar(el)`, or `ref={withOverlayScrollbar}`). Add it to any new scroll container; nothing else shows a scrollbar. Thumbs are appended to the container's parent, so give them a parent whose children are static.
- Menu items and commands that ask for input before acting (a name, a picker) end with `…` (the character, not three dots), as macOS and Windows menus do; ones that act at once or only confirm (Delete) don't.
- No rounded corners in the UI. The exception is switches, which keep the usual pill shape.
